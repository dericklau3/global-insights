# 微信公众号深度新闻写作与归档

## 目标与触发场景

把新闻线索、X 帖子、官方发布、GitHub 项目或用户提供的截图，转换成**准确、有吸引力、有内容深度、适合手机阅读**的公众号文章；用户要求时，连同文章配图和独立封面归档到 GitHub。

此 Skill 同样适用于：修改标题、按新标题重写、删去不需要的结构、为文章单独设计封面、批量处理每日新闻。不要把某一次的两个选题当成永久主题限定。

默认语言：**简体中文**。除非用户另有要求，按以下已确认的编辑偏好执行，不必反复询问。

## 不可违背的发布偏好

1. **标题要吸引人，但不能浮夸。** 要有明确事实、真实亮点、悬念或新变化，避免“杀疯了、彻底颠覆、全面碾压、史诗级”等夸张词；不以尚未验证的结果许诺读者。
2. **标题应覆盖事件的全貌，而非只盯一个数字。** 一场发布涉及多个有新闻价值的方面时，可组合 2–3 个看点并点出其意义。不能把一个大事件缩成一条参数介绍。
3. **修改标题后必须检查正文是否与之对应。** 如果标题的角度改变，要重排正文与案例，而不只是替换第一行或插入一个段落。
4. **正文不能只是发布会清单。** 讲清“发生了什么、为什么值得关注、真实案例、能用在哪里、尚有哪些限制及变化趋势”，有内容但不堆砌。
5. **适配微信公众号手机阅读。** 用短段落、自然小标题、适度加粗和穿插图片；避免大段连续文字、密集表格、花哨分割线、到处都是编号。
6. **标题后直接进入正文。** 禁止在正文顶部添加「AI 前沿」「科技产品」等栏目标签、文章整理日期、灰色引用式导语（如 `> **2026 年 10 月 14 日**`）。新闻事件本身的日期可在正文自然出现。
7. **文章正文中永远不嵌入公众号封面图**，也不写“封面设计”“封面图说明”。封面是独立文件，供后台封面位上传；正文只放有信息价值的配图。
8. **结尾不要「资料来源」或参考链接列表**，也不要附编辑说明、来源免责声明、刻意说教式“写在最后”。自然结束在事实、对比或有根据的洞察上。
9. **封面图不出现任何标题或文字。** 默认 2.35:1（例如 1175×500）；应先查找与真实事件相符的官方素材，择优裁切和适度美化。不得凭空伪造访谈、发布会、公众人物或产品形态。
10. 用户说“删除”“改一下”“重新写”时，在已明确的同一文章或同一仓库工作流中直接修改相应文件；避免只口头承诺。改动后检查、提交，并报告结果。无写入权限时明确告知且交付可复制的文件。

详细规范按需读取：[标题与写作风格](references/editorial-guide.md)、[图片与封面](references/image-guide.md)、[研究与 GitHub 归档](references/research-and-github.md)。

## 标准工作流程

### 第一步：识别需求与交付范围

- 识别输入：新闻截图、X 帖子、媒体报道、官方公告、GitHub 仓库、已有文章。
- 识别用户想要：新闻总结、公众号正文、标题优化、全文重写、真实配图、独立封面、仓库提交。
- 用户只要求标题时，不擅自重写整篇或生成封面；用户明确表示“按标题重写文章”时，调整完整结构。
- 输入足够就行动；只有缺失关键、不可推断的约束时才简短提问。

### 第二步：核实事实并筛选真正的新闻亮点

- **原始出处优先**：官方博客、新闻稿、产品文档、技术论文、开源仓库、原始 X 帖子；再参考有可信出处的行业报道。
- 截图、转述和 X 热帖是线索而不是事实证明；核对发布时间、价格、单位、地域、发布状态、测试条件。
- 提炼**核心事件 + 2–4 个不同维度的亮点**，例如技术能力、典型案例、生态布局、竞争变化、实际限制。
- 内部保留“事实—证据—适用条件”记录；无法验证的说法删去、查证或明确标注为推断。避免把厂商测试写成普遍效果。
- 不直接拼接或长篇照抄原报道，独立组织中文叙事。

### 第三步：先确定叙事角度，再写标题

- 标题尽量包含：**谁/什么 + 多个扎实看点或高价值变化**。兼顾新鲜感与可信度。
- 标题不能让读者产生“文章就只有标题这一点事”的感觉。挑选的亮点要有广度，正文要有对应深度。
- 用户要求选择时，提供 3–5 个不同力度的标题，推荐最均衡的一条；用户已明确认可一个标题，就直接执行。
- **标题—内容映射**：标题中的每个关键看点，在正文中必须有独立事实、例子、场景或解释支撑。若某亮点不足以展开，则收缩标题，不凑内容。

### 第四步：撰写或彻底重写正文

推荐叙事节奏（不是死板的编号模板）：

1. **开头**：从关键事实或读者熟悉的场景进入，前几段就说清新闻的新变化，不放模板化的引言卡片。
2. **主体**：按重要性展开 3–5 个方面；每个方面回答一个新问题，用真实数字、案例、对比或细节支持。
3. **延伸**：为什么重要、与过去有什么不同、普通人/企业/开发者能用在哪里，代价或局限是什么。
4. **结尾**：紧扣核心事实自然收束，不训诫读者，不写“写在最后”“资料来源”等附录。

按需加小标题，但**不要满篇 `01｜02｜03｜`**。不为了凑长度堆砌；默认做深入但可读的报道，而不是浅显的几百字梗概。素材有限时坦诚，而非自行编造案例。

写作细则见 [editorial-guide](references/editorial-guide.md)，初稿结构见 [文章模板](assets/article-template.md)。

### 第五步：处理正文配图和独立封面

- 正文配图必须推动理解：产品实拍、功能界面、实验画面、真实场景图、官方图表等。图片出自真实、可核查的素材；标注必要的图片说明（简短，不堆参考链接）。
- 默认封面 2.35:1、不含任何文字；先找真实官方或有适当使用授权的素材，再裁切/适度优化，不能“凭想象重画事件现场”。
- 封面独立输出至 `assets/<序号>_<主题>_cover.jpg`，**不得使用 `![...](...cover.jpg)` 插进正文**。
- 图片编辑工具缺失时不假装已经生成。能保存官方图片就保存，不能确认合法/正确图片则说明限制。
- 用户仅要求修改旧文章文字时，不需要重新生成封面。

操作规范见 [image-guide](references/image-guide.md)。

### 第六步：质量检查（必须执行）

发布前逐条确认：

- [ ] 标题信息有吸引力、不夸大、覆盖主要新闻内容；全文确实兑现标题。
- [ ] 每个主要看点至少有一个具体、可核查的事实或实例。
- [ ] 发布日期与文章写作日期没有混淆；数字、货币、地区、期限和“测试/正式上线”表述准确。
- [ ] 中文自然、段落短、手机易读、无连篇累牍的编号和教训式结尾。
- [ ] 正文无分类标签/头部日期引用框；结尾无「资料来源」/参考文献/编辑说明。
- [ ] 正文无封面图，封面文件无文字，正文图片都是真实相关素材且路径可访问。
- [ ] 未把图像示意写成真实现场；没有编造人物身份、产品外观、实验结果。
- [ ] 更新的是正确文章和日期目录，没有覆盖或删除其他文件。

对本地 Markdown，可运行 `python3 scripts/check_article.py <article.md>` 做静态检查；这只是辅助，不能替代事实核验和审稿。

### 第七步：GitHub 归档（用户要求时）

默认仓库：`dericklau3/global-insights`，除非用户指定其他仓库。默认按**北京时间的文章发布/整理日期**创建 `MM-DD/`，如 `10-14/`；用户显式指定目录时优先遵照。

建议结构：

```text
global-insights/
  10-14/
    01_主题简名.md
    02_主题简名.md
    assets/
      01_主题_cover.jpg           # 独立封面，不嵌入文章
      01_主题_01.jpg              # 正文配图
      02_主题_cover.jpg
      02_主题_01.jpg
    README.md                     # 可选：目录索引、封面链接
```

- 序号自 `01` 起递增，使用易读且跨平台安全的文件名；维护相对路径，避免重复命名和图片丢失。
- 如已有文章，保留原始路径并精确更新；更改标题时，如有索引同步更新索引标题。
- GitHub 仓库更新前检查现有结构和最新版本；只改相关文件。没有仓库权限时不要声称提交成功。
- 真实提交成功后再报告仓库路径、文章、封面、图片数量和 commit；提交后重新读取或校验文件存在。
- **修改正文时不应随意删除封面文件**；仅确保封面不嵌入正文。

更多归档与事实核验约定见 [research-and-github](references/research-and-github.md)。

## 对话快捷规则

- “标题再有吸引力一点”：加强真实看点与叙事张力，但不夸张；需要时给候选标题。
- “这篇不够惊艳/太简单”：扩大事实覆盖面，补足高价值案例与分析，**不要只添加形容词**。
- “标题改了，内容也重写”：按新标题重新排布文章章节，避免单纯局部替换。
- “不要 AI 前沿/日期”：删除正文开头的分类、整理日期、引用式导语。
- “封面不要放里面”：保留封面图片文件，删除 Markdown 正文的封面引用和文字说明；其他信息配图保留。
- “结尾不要资料来源”：删除文章结尾参考链接列表、编辑说明及分隔线；引用仍应在研究工作底稿中可追溯。
- “帮我生成封面”：先搜官方真实图片，再按 2.35:1 制作无字封面，独立存放。
- “写入仓库”：新建日期目录、依序号命名、图片归档、commit 并验收。

## 完成报告

简短汇报：**文章标题 → 文件链接 → 新增/保留的配图与封面 → 是否已经提交（commit）**。只有用户明确要看全文时才把整篇正文贴在聊天里。不要把审稿底稿和来源列表混进待发布正文。
